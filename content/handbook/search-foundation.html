01

One table, three kinds

The instinct is to add a tags table beside disciplines, and then a skills table beside that. Resist it. You would build the alias layer three times, the admin screen three times, and the search filter three times, and the three would drift apart within a month.

Instead: one terms table with a kind column. Adding a fourth kind later becomes a row, not a migration.

Discipline

What they teach

The primary facet. The only kind that generates URLs, at least to start with.

dressage
western
liberty
working-equitation

Skill

What they fix

Specific problems and jobs a rider searches for. Filters and page content, not URLs.

float-loading
starting-young-horses
confidence-building
ottb-retraining

Attribute

How they work

Practical facts that decide whether a rider bothers enquiring.

horses-available
own-arena
beginners-welcome
ndis-registered

Disciplines keep their special status. They are what a rider picks first, they order the search, and they are the only kind that gets its own page. Skills and attributes narrow a result set and add real words to a page. That split is the whole design.

Migration note

The existing disciplines and coach_disciplines tables fold into terms and coach_terms with a straight insert-select. Do it now, while there are only test coaches. nearby_coaches, getDisciplines and the profile editor all need touching either way once multi-select goes in.

02

The schema

Six new tables. The interesting ones are term_aliases, which is where search vocabulary lives, and indexable_pages, which is the single source of truth for what is allowed to exist as a URL.

-- 0007_taxonomy.sql
create type public.term_kind as enum ('discipline','skill','attribute');

create table public.terms (
  id              uuid primary key default gen_random_uuid(),
  kind            public.term_kind not null,
  slug            text not null,
  name            text not null,
  blurb           text not null default '',
  -- only disciplines start true; admin promotes a skill once the
  -- search reports prove riders search it with a location attached
  generates_pages boolean not null default false,
  active          boolean not null default true,
  sort_order      int not null default 0,
  created_at      timestamptz not null default now(),
  updated_at      timestamptz not null default now(),
  unique (kind, slug)
);

create table public.term_aliases (
  id         uuid primary key default gen_random_uuid(),
  term_id    uuid not null references public.terms (id) on delete cascade,
  alias      text not null,
  -- seed | admin | search_console | onsite
  source     text not null default 'seed',
  created_at timestamptz not null default now()
);
-- an alias belongs to exactly one term, or matching becomes ambiguous
create unique index term_aliases_lower_uniq on public.term_aliases (lower(alias));

create table public.coach_terms (
  coach_id   uuid not null references public.coach_profiles (id) on delete cascade,
  term_id    uuid not null references public.terms (id) on delete cascade,
  -- lowest-ordered discipline is the coach's primary, used in page titles
  sort_order int not null default 0,
  primary key (coach_id, term_id)
);

-- which skills/attributes to offer when a coach picks a discipline
create table public.term_suggestions (
  discipline_id uuid not null references public.terms (id) on delete cascade,
  term_id       uuid not null references public.terms (id) on delete cascade,
  sort_order    int not null default 0,
  primary key (discipline_id, term_id)
);

-- renaming a slug breaks a live URL, so keep the old one and 301 it
create table public.term_slug_history (
  kind       public.term_kind not null,
  old_slug   text not null,
  term_id    uuid not null references public.terms (id) on delete cascade,
  changed_at timestamptz not null default now(),
  primary key (kind, old_slug)
);

Areas, not postcodes

18,500 postcodes is a data source, not a page structure. Riders search for places with names: Geelong, Toowoomba, the Mornington Peninsula, the Hunter Valley. So there is a separate areas table at the level people actually type, and postcodes map into it.

create type public.area_kind as enum ('suburb','town','region','state');

create table public.areas (
  id                 uuid primary key default gen_random_uuid(),
  slug               text not null unique,
  name               text not null,
  kind               public.area_kind not null,
  state              text not null,
  parent_id          uuid references public.areas (id),
  centroid           geography(point, 4326) not null,
  default_radius_km  int not null default 50,
  -- hand-written, ~150 words. Only the top 20 need one to start.
  intro              text not null default '',
  active             boolean not null default true
);

alter table public.postcodes
  add column area_id uuid references public.areas (id);

The page register

The three-coach rule cannot live in a page component, because the sitemap, the internal links and the pruning report all need the same answer. Compute it nightly into a table and have everything read from there.

create table public.indexable_pages (
  id                 uuid primary key default gen_random_uuid(),
  -- 'area' | 'discipline_area' | 'discipline'
  page_type          text not null,
  term_id            uuid references public.terms (id) on delete cascade,
  area_id            uuid references public.areas (id) on delete cascade,
  path               text not null unique,
  coach_count        int not null,
  -- feeds a real lastmod in the sitemap. Google ignores fabricated ones.
  last_coach_change  timestamptz,
  first_indexable_at timestamptz,
  retired_at         timestamptz,
  checked_at         timestamptz not null default now()
);

-- every rider search, ours not Google's. The best gap signal you own.
create table public.search_events (
  id               bigserial primary key,
  q                text,
  term_ids         uuid[] not null default '{}',
  location_text    text,
  lat              double precision,
  lng              double precision,
  radius_km        int,
  result_count     int not null,
  clicked_coach_id uuid references public.coach_profiles (id) on delete set null,
  created_at       timestamptz not null default now()
);
create index search_events_zero on public.search_events (created_at desc)
  where result_count = 0;
Do not let the browser write to this table

An anon insert policy on search_events is an open spam endpoint. Write it from the server action that already runs the search, using the service-role client, and give the table no anon policy at all.

Admin access

The user_role enum is ('rider','coach') and it is set by the signup trigger. Do not add 'admin' to it. Adding an enum value means touching the trigger, the signup flow and every role check, and it gives an admin a role they cannot also hold as a coach. A separate table is cleaner.

create table public.admin_users (
  user_id    uuid primary key references auth.users (id) on delete cascade,
  created_at timestamptz not null default now()
);

create function public.is_admin() returns boolean
language sql stable security definer set search_path = public as $$
  select exists (select 1 from public.admin_users where user_id = auth.uid());
$$;

-- terms, aliases, areas, suggestions: readable by all, writable by admin
create policy "terms readable" on public.terms
  for select using (active = true or public.is_admin());
create policy "terms admin write" on public.terms
  for all using (public.is_admin()) with check (public.is_admin());
03

What earns a page

This is the rule that decides whether the site ranks or gets buried. Every facet you add is a temptation to multiply it by every area, and every time you give in you add thousands of near-empty pages that Google reads as doorway spam.

So there are four page types and a hard gate on two of them.

/riding-instructors/[area] is easy to overlook and it matters most. "Riding lessons" and "riding instructor" are searched far more than "coach", and neither maps to a discipline. That page is where the generic head terms land.

Room for farriers and bodyworkers

When the second profession arrives it goes in a sibling folder on the same site: /farriers/[slug], /farriers/[area]. Never a subdomain. Google treats farriers.oursite.com.au close to a separate website that has to earn its own trust from scratch, while a subfolder inherits everything the site has already built.

One rule while building: nothing that will eventually hold every profession gets the word "coach" in its path. /coaches/ is correct because it is the coaches section. A wrapper like /coach-directory/ around the whole site would not be. The terms table already has the right shape for this — a provider_type is the same pattern as kind.

The one that quietly kills directories

Faceted search URLs. Three disciplines, six skills and eight attributes generate tens of thousands of crawlable combinations, all of them thin, all of them eating crawl budget that should go to coach profiles. Set robots: noindex, follow on /search, canonical every filtered variant to the bare path, and keep filters in query strings rather than path segments so they never look like real pages.

Every coach is on a page — the fallback ladder

The gate above decides whether a page gets built. It says nothing about where a coach ends up, and that gap has a victim: the only dressage coach in Bright has a profile, no Bright page pointing at her, and no obvious answer to "so where am I listed?"

So the gate needs a partner rule. The gate governs page creation; the ladder governs coach placement. And there is one invariant worth asserting in code: every published coach appears on at least one live page, always.

A refinement to the gate itself

Make the rule three or more coaches or a hand-written intro, rather than three coaches full stop. What Google punishes is pages that are unhelpful, not pages that are short — a region page carrying two coaches and 150 real words about riding in that region is a genuinely useful page and always was.

This also hands Kim a lever. A region she cares about can go live on two coaches the moment she writes the intro, which is exactly the kind of judgement a person should be allowed to apply and a threshold should not override.

Three consequences worth building deliberately rather than discovering:

  • Location text on a profile links to the nearest live page, never to a dead one. If Bright has no page, "Bright, VIC" links to the Alpine region page. This is the internal-linking half of the ladder and it is easy to forget.
  • A rider search never returns nothing. If there are no dressage coaches within 25 km of Bright, widen automatically and say so: "No dressage coaches within 25 km of Bright. Here are the four nearest, 30–80 km away." An empty results page is the worst moment on the site and it is entirely avoidable. Log it as a supply gap either way — see section 07.
  • Tell the coach where she is, and when that changes. The dashboard lists the pages she currently appears on. When her suburb reaches three coaches and the page goes live, she gets an email. Better still, tell her how far off it is: "Two more coaches in Bright and we'll build the Bright page. You'll be on it."

That last line quietly turns the weakest thing about a thin area into a recruiting prompt aimed at the person best placed to act on it. She knows the other two coaches in town, and the referral scheme already gives her a reason to call them.

Assert the invariant, don't assume it

Add a check to the nightly eligibility job: count published coaches with zero live pages. It should always be zero. If it ever isn't, something in the gate, the ladder or the area mapping has broken silently, and the symptom — a paying coach who is invisible — is the single worst bug this site can have.

Surface the count in the weekly digest alongside the search-gap reports. One line, almost always reading zero, and the one week it doesn't is the week it earns its place.

04

Multi-discipline, both directions

Two separate problems: a rider who wants to search several things at once, and a coach who teaches several things.

Rider side

The convention riders already expect from every job board and property site: OR within a kind, AND across kinds. "Dressage or show jumping" and "travels to you" and "confidence building". Passing one flat array with a match-all flag cannot express that, so pass three arrays.

create or replace function public.nearby_coaches(
  p_discipline_ids uuid[] default null,
  p_skill_ids      uuid[] default null,
  p_attribute_ids  uuid[] default null,
  p_lat            double precision default null,
  p_long           double precision default null,
  p_radius_km      double precision default 50
) ...

-- one of these blocks per array; OR inside, AND between
and (
  p_discipline_ids is null or cardinality(p_discipline_ids) = 0
  or exists (
    select 1 from public.coach_terms ct
    where ct.coach_id = cp.id and ct.term_id = any(p_discipline_ids)
  )
)

Sort by distance as now, but break ties on how many of the selected terms a coach matches. A coach who ticks four of your five filters should sit above one who ticks two at the same distance.

URL shape: /search?d=dressage,show-jumping&s=confidence-building&near=3550&km=50. Slugs rather than UUIDs, so the URL is shareable and readable, resolved server-side.

Coach side

A coach appears on every discipline × area page they qualify for. That is correct and it is free reach. The only thing needing a decision is which discipline leads their page title and card, and coach_terms.sort_order answers it: lowest-ordered discipline wins, and the coach reorders by dragging in the profile editor. No extra column, and it gives them control over how they are presented.

Their profile page then reads: Dressage and show jumping coach in Geelong VIC, with the rest listed underneath.

Suggested terms

Seed term_suggestions by hand so a coach picking Western immediately sees reining, campdraft, colt starting and stock work offered. Once ten or more coaches share a discipline, add a second row computed from what they actually picked: "Other Western coaches also list…". Curated first because there is no data yet, then data-driven as it arrives.

Cap the suggestion list at eight or so. A wall of checkboxes gets skipped, and a half-tagged profile is worse than a focused one.

05

Where aliases go, and where they must not

Aliases exist so that a rider typing "flatwork coach" finds your dressage page. They are a matching layer, not page content. The failure mode is dumping the list somewhere visible, which is textbook keyword stuffing and precisely what the 2024 updates hunt for.

Four legitimate places, and only four:

  • The title tag. Dressage Coaches in Geelong VIC | Riding Lessons & Instructors. One primary alias, worked into a real sentence.
  • One natural sentence of body copy. "Find dressage instructors and flatwork coaches near Geelong." Not a list.
  • Internal link anchor text. Vary it across the site. Some links say "dressage coaches", some say "dressage instructors". Identical anchors everywhere is its own signal.
  • Structured data. knowsAbout on the coach, alternateName on the term. This is where a machine-readable list actually belongs.

Mark one alias per term as the primary so the title generator is deterministic rather than picking at random. Everything else stays in the database doing matching work.

// coach page schema — Person for individuals, LocalBusiness for schools

  "@context": "https://schema.org",
  "@type": "Person",

  "jobTitle": "Riding Coach",
  "url": "https://…/coaches/marnie-tolhurst",
  "image": "…",
  "address": { "@type": "PostalAddress",
    "addressLocality": "Geelong", "addressRegion": "VIC", "addressCountry": "AU" },
  "areaServed": [{ "@type": "City", "name": "Geelong" }],

Area pages get ItemList wrapping the coach cards, in the order shown. Add BreadcrumbList on every page below the top level. Neither is glamorous and both are a few hours of work with a disproportionate return.

06

The admin screens

Yes, admin-editable, and it is not a nice-to-have. Sport vocabulary shifts, new disciplines surface, and the reports in the next section will hand you new alias candidates every week. Hard-coding vocabulary means a deploy for every word, which in practice means the words never get added.

Three screens under /admin, gated on is_admin() in the proxy and again in RLS:

  • Terms. Create, rename, reorder, deactivate. Toggle generates_pages. Deactivate rather than delete, always, since a deleted term silently unpicks itself from every coach who chose it.
  • Aliases. Add and remove, with the source shown. A one-click "add as alias" button on each row of the unmapped-query report, which is what closes the loop between reporting and vocabulary.
  • Areas. Edit the hand-written intro, adjust radius, activate or deactivate. Shows current coach count and indexable status per area.
The slug trap

A term's slug is in a live URL the moment generates_pages is true. Editing it in an admin form silently 404s every indexed page under it and throws away months of ranking.

Two guards. Make the slug field read-only in the UI once the term has ever been indexable, with a separate deliberate "change URL" action behind a confirmation. And have that action write the old slug into term_slug_history, with middleware issuing a 301 from any historical slug. Same pattern for areas.slug and coach_profiles.slug, which has exactly the same problem the first time a coach edits their display name.

07

The reports that find your gaps

You have two data sources and they answer different questions. Google Search Console tells you what people typed into Google and whether you appeared. Your own search log tells you what they typed into your box and whether you had anything to show them. The second one is the one nobody else has, and it is the more useful of the two.

The loop this is all for

Every report exists to feed the next week's vocabulary and the next month's recruiting

1Riders searchOn Google, and in your own search box. Both get logged.
2Weekly reportFinds queries that matched no term, and searches that returned nothing.
3You add wordsOne click adds an alias, or creates a term, in the admin screen.
4Pages improveTitles, copy and matching all pick up the new vocabulary.
5Rankings moveNew queries start landing, which produces new gaps.
Then back to step one. Roughly fifteen minutes of your attention a week, which is the only budget this has.
1

Unmapped queries

Pull Search Console queries and on-site searches, strip location tokens and stop words, then list anything that matches no alias. Rank by impressions and by on-site frequency.

This is your alias pipeline. Most rows will be junk, some will be words you had not thought of, and one a month will be a discipline you did not know existed. Each row gets three buttons: add as alias to an existing term, create a new term, or ignore permanently.

2

Zero results, split two ways

On-site searches that returned nothing, separated into two very different problems:

  • Supply gap. The words matched, but there is no coach in that area. This is a recruiting list, ranked by demand. It answers "which region do we go into next" with evidence instead of a guess.
  • Vocabulary gap. The words matched nothing at all. Straight into report one.

Distinguish them by re-running the query with the location dropped. If it returns coaches, it is a supply gap.

3

Performance by URL pattern

Group Search Console page data by pattern rather than by page: /coaches/*, /disciplines/*, /disciplines/*/*, /riding-instructors/*. Impressions, clicks and average position for each.

This tells you which page type is earning its keep, which is the thing total-traffic dashboards hide. It also produces the prune list: any page with zero impressions in 90 days gets merged or retired.

4

Near misses

Queries where you rank position 5 to 20 with real impressions. The page already exists and Google already thinks it is roughly relevant. These are the cheapest wins on the site and usually need a hundred more words of intro, a better title, or two internal links.

5

Promotion candidates

Skill and attribute terms that appear in real queries with a location attached. "Float loading training Melbourne" is the signal that float-loading has earned generates_pages = true.

This is the mechanism that lets the page structure grow without ever guessing. Nothing gets a URL until riders have demonstrated they search for it that way, which is the opposite of how directories usually expand.

Wiring it up

A service account against the Search Console API, not OAuth. It does not expire, needs no refresh token and runs headless. Three steps: enable the API in Google Cloud, create the service account and download the JSON key, then add the service account's email as a user on the Search Console property. Skipping that third step is the usual cause of a 403.

The job itself is a Vercel Cron hitting a route handler, guarded by a CRON_SECRET header check so it cannot be triggered from outside. It writes findings into a seo_findings table and sends one digest email through Resend, which you already have wired for clinic notifications. The email is the product here. A dashboard nobody opens is worth nothing at 1 to 5 hours a week; an email with five rows and three buttons gets actioned.

08

Freshness and upkeep

Directory pages go stale in a specific way: the page stays identical for a year while the underlying reality changes. Two coaches stopped teaching, one moved, three clinics came and went. The fix is not to rewrite pages on a timer. It is to make the page reflect things that genuinely change.

Rendering

  • Coach pages. Static with a long revalidate, plus on-demand revalidatePath the moment a coach saves. Content the user just changed should never wait for a timer. Revalidate their area pages in the same action.
  • Area and discipline × area pages. ISR at an hour, plus on-demand when a coach in that area publishes, unpublishes or lapses. generateStaticParams reads indexable_pages, so an ineligible combination never gets built at all.
  • Sitemap. Generated from indexable_pages with lastmod taken from last_coach_change. Real values only. Google learned to ignore sitemaps where everything changed today. Split into a sitemap index once you pass about 5,000 URLs.

Genuine freshness, not manufactured

  • Clinics are the freshness engine. They have dates, they expire, and they turn over by themselves. An area page that lists upcoming clinics changes honestly and often. Past clinics move to a history section on the coach page rather than vanishing, so the words stay.
  • Stale profile nudge. Any coach untouched for six months gets an email asking them to confirm they are still taking students. Fresher content, and it catches coaches who quietly stopped teaching before a rider wastes an enquiry on them. It doubles as a retention touchpoint.
  • New testimonials change the page in the way that matters most, since they are content that exists nowhere else. Prompt for them in the monthly coach email.
Set this up before there is traffic

Verify the domain in Search Console and submit the sitemap the day the site goes live, even with twelve coaches on it. Search Console only holds 16 months and only starts collecting from verification. Every week you wait is a week of baseline you can never get back, and the whole reporting loop above is worthless without history to compare against.

10

Outranking who is already there

Nobody owns "riding instructor near me" in Australia, but the results page is not empty. Four kinds of thing turn up, and each loses for a different reason. Knowing which is which tells us where the effort goes.

Coaches4U, in detail

Worth studying because they have built exactly the site this specification is designed to avoid, and they have built it first.

Their URLs run /directory/category/equine-sports/location/nsw/sydney-region/, with a deeper variant adding a discipline and a sub-region. So they hold the full programmatic matrix: discipline × state × region × sub-region, generated whether or not there is anything on the page.

The Sydney page — the largest equestrian market in the country — carries thirteen listings. They are mostly riding schools and equestrian centres rather than individual coaches. There is no written content about Sydney, no content about dressage, nothing a person composed for that page. The body copy describes the platform.

The title-tag collision

They already occupy the pattern "Horse Riding Coaches in the Adelaide Region". If we publish "Horse Riding Coaches in Adelaide" we are competing on near-identical strings with a site that has more history than us.

Differentiate on specificity and intent instead: use the suburb or town rather than the region, lead with the discipline where we have one, and use the words riders actually type. "Dressage Coaches in Strathfieldsaye VIC — riding lessons near you" beats competing head-on for a broader phrase we would lose today.

A fixed basket of queries, checked monthly

Pick twenty queries at the start and never change the list — the value is in watching the same ones move. Roughly: five "riding instructor / riding lessons + town", five "[discipline] coach + town", five long-tail skill queries such as float loading help Bendigo, and five brand queries.

Record our position and whether Coaches4U, EquiDirectory or the EA register appear above us. Search Console gives us our own positions for free; the competitor check is a manual look, ten minutes a month, and it goes in the same monthly review as the search-gap report from section 07.

The long-tail skill queries are where we win first. Nobody has written a page about float loading help in a particular town, and those are the searches the skills facet exists to catch.

One thing not to do

Do not respond to a competitor by widening. The instinct on seeing a matrix of thousands of pages is to build a bigger matrix. That is how a small site with 400 good pages turns into a large site with 200,000 bad ones, and it is the only mistake in this document that cannot be undone quickly.
